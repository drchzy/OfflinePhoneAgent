## C. 三层协作理念页的确定

12. 用户提出理念：“人与人、人与 AI、AI 与 AI”更容易体现协作升级，但担心说 AI 与 AI 会让人消失。
13. 后来最终确定：“人与人协作 → 人与 AI 协作 → **人主导的多 AI 协同**”。
14. 用户要求明确**每阶段人决策什么**：第一阶段人讨论、协调、开发和验收；第二阶段人定目标/约束、指挥 AI、审核；第三阶段人定义角色/架构边界/质量要求、处理关键问题、最终整体验收，Lead 与多个 Agent 承担具体协同执行。
15. 这页作为方法论提升/引出 Super App 的单独一页；不是替代原先的行业痛点开场。

## D. Super App：基础机制、质量缺口与渐进升级

16. 用户明确已定义多角色、角色之间可投递任务。测试 Agent 找到 Bug，可以找任务最初的**开发 Agent**去处理，而不是换一个完全陌生的新对话。
17. 每张任务卡应记录各前置角色与**会话 ID**：谁开发、谁测试、谁验收、何时被打回。目的在于恢复原上下文、减少返工理解成本。
18. 人更多与 Lead/总指挥/架构师 Agent 沟通，确定最初角色及规范；流程各阶段执行与转交由 Agent 承担，完成后人整体验收。
19. 用户指出：原来多 Agent 设计、开发、功能测试等工作都有，后来人工打开应用发现某些页面**功能测试过了，但与原型不一致**。
20. 于是新增“**产品验收 Agent**”及其独立角色提示卡和阶段；它是后加的质量提升项，**不是说整个协作流程从零搭建**。
21. 新角色需要提供**高保真原型与实现页面的截图对照**，不是说“做完了”就放行。
22. 发现不一致后，即使此前状态是完成，也要重开任务，沿任务卡/会话 ID 回派原开发角色、修改、复测、产品重新验收；最后由人整体验收。
23. 用户发现“看截图还不足以精确调样式”，进一步要求开发/产品验收角色**读取原型源码**中的 CSS/组件、间距、字号、配色和交互参数，减少 AI 对视觉的想当然。
24. 因这些问题，用户让架构/开发等角色更新各自的**提示卡和流程约束**，形成可复用规则。该行为是人工发现 AI 缺漏并提升协作制度，而不是纯工具堆叠。
25. 用户补充：拿到高保真原型之初，本就先用 AI 做**技术架构设计+UI/UX/UE 分析与提示词**，再统一派给开发实现。
26. 动效最终表达应该是：**展示原流程 → 暴露测试通过但原型不一致 → 插入产品验收 Agent 节点 → 出现源码/截图比对 → 拒签与回派复验 → 人最终验收**。
27. 用户反复确认：新增的是**产品验收阶段及其证据链**；已有开发/测试、任务看板、会话追踪和普通缺陷回派仍应保留其原有地位。
28. 用户说明终极目标：**提升 AI 开发产出质量**，不是为了多一个 Agent、不是声称 100% 完美还原。
