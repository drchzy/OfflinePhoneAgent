## 一、不可丢失的总目标

**竞赛作品**：AI 驱动的研发协作模式创新与工程化实践；对外讲述重点是研发协作模式升级，而不是单纯“AI 生成了多少代码”。

**听众**：技术及管理评委。**时限**：讲解和实物演示合计 15 分钟；需至少 3 个不同研发环节 AI 协作记录（提示词→AI 输出→人工判断或采纳理由），并现场复现真实 AI 协作生成。不可用纯录屏或 PPT 动效替代真实运行。

**已确认的叙事入口（必须恢复）**：
1. 先讲真实行业/研发痛点：跨岗位重复转译、产品原型等待与评审、前后端接口沟通、测试返工、部署文档与项目交接成本，而不是开门见山直接讲“AI 覆盖全流程”。
2. 再讲创新方式：AI 从个人工具升级为团队研发基础设施；通过共同的工程规范、接口契约、角色卡、文档与任务过程降低沟通。
3. 用沈阳文旅、福州科技馆商城与 APP、SRS 音视频复杂联调、Super App 多 Agent 等真实场景支撑，不按单一项目从头到尾流水账。
4. 中后段讲“人与人协作 → 人与 AI 协作 → 人主导的多 AI 协同”的方法论，突出每阶段人负责哪些决策，**绝不是把人从协作中移除**。
5. 再引出 Super App 的具体设计与质量升级、接入现场演示，最后落到证据、可复用成果和边界。

## 四、进一步补充的真实项目能力（2026-11-21 ~ 11-22 对话）

### 4.1 沈阳文旅：从个人使用到 Skill 资产
- 在文旅阶段已提炼前端、后端、底层框架等 Skills 与习惯规范。
- 迁移到福州科技馆后，AI 按既有工程架构、依赖、接口规范、组件调用生成新功能。
- 复用的价值在于减少重复解释系统边界，不是把第三方安装包全部当原创。
- 个人提效 → 规范化实践 → 团队可共享复用是连续演进。

### 4.2 福州科技馆商城：产品、开发、前端跨岗位协同
- 后端开发者具备上一个商城项目经验，利用已沉淀 Skills，先搭建商城可体验的 V1，而不是必须等待新产品岗位完整原型和多轮评审后才动工。
- 产品负责目标、关键需求、重要信息与整体交互把关，先体验已有成果再反馈迭代。
- 不等于完全取消产品评审：是**在满足关键业务边界的前提下减少不必要的串行等待**。
- 开发者同时用 AI 生成 H5 页面走通后端 API 和业务流程，自测接口、入参出参、异常及 UI 调用。
- 交前端时交付接口文档 + H5 联调代码/示例，帮助前端减少重复问答；前端仍对体验与专业细节完善负责。
- 测试反馈以交互体验问题相对突出，不能据此宣称 Bug 已量化降低，必须后续从真实 QA 记录核对。
- 典型流程：业务方向 → AI 辅助实现可体验版本 → 产品确认 → API/H5 自测 → AI 接口文档发布 → 前端续作 → QA。
- 讲业务价值时用少量谨慎、可复核数字；无真实历史基线不宣称数百倍/上千%提效。

### 4.3 福州科技馆：一键初始化和文档交接
- 新项目一键形成 AI 研发环境，包含 docs、Skills、MCP 配置、AGENTS.md、功能变更记录、迭代看板、自动测试相关目录/脚本、部署资料与运行信息。
- AGENTS.md 汇总项目介绍、功能、技术栈、运行方式和必要规范；**公开资料不得包含测试密码、生产地址、凭据**。
- 部署记录和服务器基础情况放 docs 等可定位文档；接口文档 Skills 在生成之后同步到文档平台，减少人工搬运。
- Git / change 历史、会话与任务记录能够生成阶段交接文档，接手同事按文档与原工程上下文继续开发。
- 需严格区分“已有目录或规则”与“所有质量门禁均自动执行成功”。
- Super App 多 Agent 工作流是之后计划整合进入这套初始化框架的**升级目标**，不能倒写成科技馆已部署。

### 4.4 SRS 音视频复杂联调与跨系统排障【重要遗漏，必须恢复】
- 用户明确点名以前确定过多个 SRS 音视频复杂联调/调试场景，后续 16 页 HTML 中被遗漏。
- 已知可追溯技术素材：SRS/RTC 播放端回调 on_play、HTTPS 回调读取失败、前端/流媒体服务/业务 API/反向代理与服务器日志联动定位；必要时通过 SSH MCP、接口查询、浏览器/客户端验证，多层检查而非凭单个报错直接下结论。
- 原始故障属于具体真实技术记录，**当前公开归档只写脱敏诊断链**，不包含实际服务 IP、token、流 ID、客户地址等。
- 演示表达应覆盖：症状 → 假设 → AI 协助提出检查点 → MCP 查询真实日志/配置 → 人决定下一步验证/修复 → 结果/证据 → 规则沉淀。
- **具体根因、完整多场景清单、各场景已复现实测与最终修复 commit 仍待核**；不能因用户提到了联调就把根因与成功率编出来。
- 与商城 H5/接口联调互补：前者体现跨系统疑难排障深度，后者体现跨岗位开发协作。

### 4.5 其他不可丢失的复杂 AI 纠偏实例
- **权限/闸机相关问题**：AI 一度采取绕过安全校验方式，人明确否决不安全捷径，改查真正启动依赖问题；证明人管安全边界。
- **出票恢复/数据库连接异常**：先按同一批次口径核对出票状态再决定是否修复，不把时间点不一致的统计当对比。
- **多实例重复结算与对账**：不把五秒窗口噪声当真实增量，统一数据状态/比较口径。
- **商品/库存策略及信创适配等**：可做工程深度备选，但演示要按 15 分钟挑选，不能堆成十几个案例。
- 每个案例至少给出输入、AI 分析、人工纠偏、结果与证据；仅文档陈述和源码文件存在不能等同生产验证。

## 五、三阶段协作理念页（新增，不取代 V1.0 痛点开场）

用户确认在**不推翻既定 PPT 结构**的前提下，增加一页方法论：
1. **人与人协作**：人负责需求讨论、分工、评审、开发、联调和验收，AI 用文档/对照降低沟通。
2. **人与 AI 协作**：人定义需求、技术边界、质量标准，AI 在授权范围内执行代码/文档/测试，人控制关键节点。
3. **人主导的多 AI 协同**：人制定目标、角色边界、约束和最终验收；Lead/架构师 Agent 统筹任务、多个 Agent 各司其职、互相交接/回派；人介入关键冲突或例外。

**人的责任不会消失**；从亲自处理具体事项到定义规则、关键决策、组织协同和最终验收。三种模式叠加，不是互相替代。此页自然引出 Super App，而不是开场的第一页。

## 六、Super App：已运行机制与后期质量升级

### 6.1 已有基础机制
- 用户自建多 Agent/多角色分工、团队章程与提示卡：产品、架构、开发、测试、Lead 以及后续产品验收等，实际名称以工程角色卡为准。
- Lead/总指挥掌握任务整体状态与分工，人主要与 Lead 对话，定义目标、原则、质量标准和最终验收。
- 任务卡承载需求、生命周期状态、角色、会话 ID、历史记录及检验线索，支撑任务追踪和上下文复用。
- 测试发现 Bug 后按任务卡追溯原开发 Agent / 原会话，回派修复、复测，减少重新解释上下文。
- 原有任务回派、会话追踪、开发、测试流程本来就有；**千万不要说它们是在新增产品验收 Agent 时才首次出现。**

### 6.2 设计规范前置
- 高保真原型到手后，AI 先参与技术架构分析、UI/UX/UE、组件、配色、字号、间距、交互流程、页面状态等规范与提示词提炼。
- 提炼后统一派发给开发角色实现，而不是让开发猜测设计意图。

### 6.3 真实触发的后期流程升级
- 发现“功能已测试通过、状态被标为完成，但实际页面与原型有明显视觉或交互差异”。
- **升级点是新增独立的“产品验收 Agent”阶段**，把原流程“设计→开发→测试→完成”变为“设计→开发→测试→产品验收→完成”。
- 要求产品验收 Agent 对照原型与实现截图；还要求读取**原型源码**，提取样式、尺寸、布局、交互约束，而非只凭视觉猜测。
- 发现差异，即使任务之前标为 done，也允许重开/拒签并回到原开发角色，会话衔接、改完复测再产品验收。
- 截图比对、证据留存与针对产品一致性的退回规则，是新增产品验收阶段的重要补强；既有通用缺陷回派机制并非新加入。
- 反复出现的缺陷触发修改角色提示卡/测试与产品验收规则，形成“发现偏差→人工判断→规则升级→后续减少重复错”的学习型研发流程。
- **目的**：提高 AI 开发交付质量，不是保证 100% 还原；效果没有完整独立验收统计，不虚构一致性百分比。
- PPT 用“原流程 → 暴露问题 → 动态插入产品验收 Agent → 对比截图+源代码 → 拒签回派/复测 → 人工最终验收”演进动画最清楚。

### 6.4 静态证据与边界
- 2026-11-20 审计快照记录 67 张任务卡、55 条 status=done、12 blocked、263 条日志；**不等于 55 个已独立验收的交付功能**。
- 团队模板有 7 类角色；看板 checks 某些判断根据日志关键词推导，不能称不可伪造的硬门禁。
- 有浏览器验收、截图、CSS 对比、任务拒签线索；原始截图链/独立会话/某些真实自动投递尚需工程复核。
- 有历史线索称多 Agent 子会话、被退回任务等，但未从所有原始记录重新独立核验，暂不在 PPT 写成经实测确证的数量。
- **不是已在福州科技馆全面融合上线的生产级 Agent 平台**，后续计划吸收其流程到统一一键初始化体系。

## 七、竞赛现场演示安排的变化

先前版本曾把现场演示作为单独页面，用户要求把真实演示自然融入 **Super App 那一页**，讲多 Agent 派发时切到真实工程，演示结束回 PPT 引出产品验收升级。

建议示例：任务卡会话 ID 的“一键复制”小功能，需先核验是否未实现，若已存在就换成真实未实现的小任务。现场展示：
1. 人给 Lead 明确目标、范围、验收标准；
2. Agent 拆任务并产出实际代码 diff / 实现效果；
3. 运行可复核的本地测试或检查；
4. 看任务卡、会话关联及测试/验收流转（真实做到哪一步就展示哪一步）。

时长内不能假设每项自动化都完成；禁止伪造输出、绕过安全和在生产环境临时危险修改。
**项目初始化本身**在工程标准化部分通过目录/规则实际存在来证明，不必现场从零搭全项目。
